## Step order (from `docs/mercury.md`; each ends with its test green, then a commit)

Step 0 is new and comes before everything, including the task registry. Do not skip it to get to the interesting work: it is the cheapest it will ever be, and every step after it adds a process that would otherwise be invisible.

0. **Observability, before anything else.** Right now tracing is configured and traces nothing, and every step below adds a process that would also emit nothing. Two processes are cheap to correlate; five across two languages are not. Four faults to fix, all verified against the live deployment: move `FastAPIInstrumentor.instrument_app` out of the lifespan into `create_app()` after the routes are added, because Starlette has already built the middleware stack by lifespan time and the patch silently does not take; call `configure_telemetry()` from the worker's `main()`, which never calls it at all although the deploy already passes it the connection string; set `OTEL_SERVICE_NAME` per role in the Bicep, which has no `OTEL_*` variables today, so both roles land under the SDK default name; and **persist a W3C traceparent on the run row when the run is created, restoring it in the worker before the loop starts**, which is the only one that is design rather than a moved call and the only one that makes a run a single trace.

   Then structured logging. Every process writes JSON to stdout, which the managed environment already ships to the workspace. Not through the exporter: logs must keep working in CI, in local compose and on the self hosted machine, none of which have one. Fields: timestamp, level, logger, message, run id, run type, step sequence, worker or replica id, trace id, span id. The API currently never calls `basicConfig` at all, so its own log calls do not emit; fix that too. **Never log a task input body or a model output.** One root span per run with a child span per loop step carrying kind, provider and tokens; a takeover gets a child span marked as such and stays in the same trace.

   *Exit: an in memory span exporter test asserting the API's root span and the worker's spans share a trace id and that each step is a child span; a test asserting `OpenTelemetryMiddleware` is present in the built middleware stack, because its failure mode is silent and that is exactly the bug that survived before; and README claim eight green.*

1. **Task registry, provider per type, and the run list endpoint.** `app/tasks.py` with a `TaskType` dataclass (name, tools, provider, budget, public) and the five entries. `runs.type` column by migration, default `pytest` for existing rows, plus a nullable `executor` column used only by checks. `POST /runs` takes `type` and `inputs`; the worker picks the provider from the registry, not from `MODEL`. Config gains `PROVIDERS` as a mapping of name to base URL, key variable and model. **`GET /runs` with a serializer**: metadata only (type, provider, executor, status, tokens, duration), newest first, keyset pagination on `(created_at, id)`, default 50 and max 200, behind the existing public rate limit. It is here rather than with the page because the chat tools and `curl` both want it first. `tests/test_tasks.py` and `tests/test_run_list.py`. Existing tests still green.
2. **Scheduled Job, site checks, and the self hosted check worker.** Four commits, because this is the largest step in the brief and only the first part is needed before step 3 can start.

   **2a. The scheduler and a cloud side check.** `infra/main.bicep` gains a Container Apps Job, cron trigger, that runs the same image with `ROLE=scheduler` and posts the due tasks to the api with the bearer token. `site_check` type: HTTP status and latency for the URL, no model call. Schedule read from the mounted config. The scheduler gets its own `OTEL_SERVICE_NAME` and **must flush spans explicitly before exit**, or a Job that runs for seconds dies with its spans unsent. Suspension lands here too, because it needs the scheduler: a small table keyed by schedule name holding the consecutive failure count, a suspended flag and when it happened, checked before a run is created. Three consecutive failures suspends until resumed by an inline button on the suspension message, with a command as fallback, shown in `/status` and the digest. It is what stops a retry storm burning the workspace's daily ingestion cap on the day the logs matter most. *Exit: the log line `scheduled run <id> created with no client` from the live deploy, a test that a task suspends on the third consecutive failure and resumes, and README claim one green.*

   **2b. The claim endpoints.** Three, all behind the bearer token: `POST /checks/claim` (the body declares which kinds the worker can run, returns one pending `site_check` of those kinds with its lease, or 204), `POST /checks/{id}/heartbeat`, `POST /checks/{id}/result`. They reuse the existing two minute lease rather than inventing one. The `executor` column is written here. **Claim must never return a `pytest`, `chat`, `repo_chore` or `digest` run.** *Exit: `tests/test_claim_endpoints.py` green, including a test that asserts claim refuses every type except `site_check` of the declared kinds.*

   **2c. The worker, Lighthouse only.** `checks/` is a Node 22 and TypeScript service with its own `package.json` and no workspace. It polls claim, runs Lighthouse, heartbeats, and posts a result of about 1 KB: the five category scores, largest contentful paint, total blocking time, and the ids of the audits that failed. The full report is discarded. The result is a summary, stored where the 30 day cleanup will not reach it. `ci.yml` gains a Node job. It writes the same JSON log fields as the Python side, minus trace and span ids it does not have, plus the executor, and sends the last fifty lines of its log with the result **on failure only** so a failed check is debuggable from the runs page without touching that machine. *Exit: `checks/` unit tests green with a faked HTTP side and a stubbed Lighthouse call, and one real check visible in the runs list with `executor` set.*

   **2d. The crawl, the fallback, and the self hosted deployment.** Add the same origin link crawl: depth 3, 200 pages, 10 second timeout, robots.txt respected, only 4xx, 5xx and timeouts reported. Add the fallback: a pending check unclaimed for `CHECK_CLAIM_WINDOW`, default 30 minutes, goes to the cloud PageSpeed path, and a lapsed lease returns the check to pending where the window applies again. **A posted result is terminal whatever it says, so a site returning 500 is a finished check with a bad finding and is never retried elsewhere.** Add `checks/compose.yml` with Node and Chromium and restart `unless-stopped`. *Exit: one real Lighthouse integration test against a locally served page in the compose job, a test exercising the fallback window, and README claim seven green.*
3. **Telegram webhook, chat, progress.** `POST /telegram` verifies the secret token header and the chat ID, maps free text to a task through the model with the registry as the schema, handles `/status`, `/runs`, `/cancel`. Progress is one message edited as events land. `tests/telegram_fake.py` is the fake server. Cold start measured with timed log lines on the live deploy and written into the README as a number.
4. **Approvals and repo chores.** `approvals` table, inline buttons, 24 hour expiry. `repo_chore` clones into a temp directory, branches `agent/<run id>`, runs the repo's tests, pushes, opens the PR with the GitHub token. No PR on red. Takeover checks the remote for the branch first. Integration test against `mercury-fixture`, marked `integration`.
5. **Digest, audits, cleanup.** `digest` type at 07:30 Melbourne. CI failure watch hourly through the Actions API. `pip-audit` and `npm audit` weekly with findings in the digest only. Cleanup task deletes event bodies older than 30 days and **must leave check summaries alone**, or the digest can never say a score moved. Write the test that proves a summary survives the cleanup.
6. **The runs page as a React app, then the claims.** Four commits. Get the pipeline working before writing any interesting React, so a broken build is never confused with a broken component.

   **6a. The pipeline, with a near empty page.** `web/` is Vite, React and TypeScript with its own `package.json` and Node 22. The Dockerfile becomes multi stage: a Node stage builds `web/`, the Python stage copies the output, and the existing `COPY` list gains it. **FastAPI serves the bundle at the root, not nginx**, because the cloud deployment has no nginx and serving from nginx would make local and production disagree about the one thing this page demonstrates. API routes take precedence and unmatched paths fall through to the page. Both `ci.yml` and `deploy.yml` gain a Node job running typecheck and Vitest. *Exit: a page saying nothing but its own title loads from the deployed image, and both workflows are green.*

   **6b. The runs list.** Reads `GET /runs`, newest first, showing type, provider, executor, status, tokens and duration, with the keyset pagination the endpoint already serves. Metadata only. *Exit: the list renders real runs from the live deploy, and a Vitest test covers the pagination boundary.*

   **6c. Run detail and the stream.** A `useRunStream` hook holding an `EventSource` that merges events by their monotonic id, resumes with `Last-Event-ID` without duplicating rows, and drives the kill connection button. **No login and no token in the browser:** metadata for every run, full event bodies only for task types flagged public. Scope stops here; Telegram owns approvals and chat. *Exit: Vitest and React Testing Library tests against a fake `EventSource` covering the merge on reconnect and the duplicate id case, plus README claim six green.*

   **6d. The claims table, then the rename.** Paste test output under each of the seven rows. Only once every row is green, rename the repo to `mercury` on GitHub, and update the README title, `CLAUDE.md` and the private repo's image reference in one commit. *Exit: seven green rows and a repo called mercury.*

## What not to do

Do not leave the design document's paragraph about tracing tracing nothing in place once step 0 is done; replace it with a short section on what is traced and what is logged, and delete the fault list. The git history keeps the reasoning. The README gains a short observability section, because this is a claim now. Do not merge or publish anything from a task. Do not add a paid resource; the Job and the webhook exist so nothing stays awake. Do not use long polling. Do not pin `latest` in the private repo. Do not mention my employer, its customers or its code anywhere. Do not write a README claim before its proof exists. Do not put a token in a commit, a log line or a Telegram message.
